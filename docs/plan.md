# 산업용 라벨 OCR Fine-tuning 기획서 (plan.md) — 수정본 (혼동 문자 정제 완료 반영)

> **문서 역할 갱신**: 이 문서의 **실행 지시 역할은 `claude_code_prompt_paddleocr_colab.md`로 이관되었다.** 실제 fine-tuning 작업은 그 문서를 단일 진실 공급원으로 참조한다. 이 문서는 이후 (1) 도메인 규칙이 왜 확정됐는지에 대한 **의사결정 근거 저장소**, (2) 앱 개발 단계 `System_Architecture.md`의 **재료 출처**로 유지한다. 두 문서와 실제 구현 사이에 불일치가 발견되면 `claude_code_prompt_paddleocr_colab.md`가 우선한다.

## 0. 문서 목적 및 범위

정제된 라벨 데이터(`Label.txt`)를 기반으로, 산업용 자재/부품 마킹 코드 인식 OCR 모델을 fine-tuning 하기 위한 실행 계획을 정의한다. 데이터 진단 결과를 반영해 "무엇을 / 왜 / 어떤 순서로" 진행할지 명확히 한다.

### 이 문서의 범위(Scope)
- **In scope**: 라벨 정제, 데이터 분할·증강, 모델 fine-tuning, 평가 절차, 곡면 대응, 그리고 **주 KPI 측정에 필요한 최소한의 후단 DB·매칭 프록시 정의**.
- **Out of scope(별도 문서로 분리)**: 상용 DB 인덱싱·검색 인프라 상세, 세부 아키텍처 설계, 배포·운영 파이프라인. 단, 이들이 KPI 측정을 좌우하는 부분에 한해 이 문서는 **평가용 baseline만** 규정한다.

> **문서 분리 로드맵**: 본 수정본에서 아래 항목들이 확정된 후, `Training_Strategy.md`(모델·하이퍼파라미터), `System_Architecture.md`(Detection→Recognition→DB Matching→UI), `Evaluation_Plan.md`(KPI·검증셋), `Data_Quality_Guideline.md`(라벨 품질·승인·버전관리)로 분리한다. 정의 이전 분리는 빈 문서 양산이므로 순서를 지킨다.

## 1. 데이터 현황 (수정본 기준)

> 본 계획은 `Label.txt`(경로+어노테이션) **및** 원본 이미지 파일 2,340장 두 자산을 전제로 한다. `Label.txt`는 이미지 경로만 담고 있어 실제 이미지 파일 없이는 크롭·학습이 불가능하다(실행 세부는 `claude_code_prompt_paddleocr_colab.md` TASK 0의 이미지 자산 정합성 검증 게이트 참조).

| 항목 | 값 |
|---|---|
| 이미지 수 | 2,340장 |
| 텍스트 박스 수 | 8,103개 |
| 이미지당 평균 박스 | 약 3.46개 |
| 고유 텍스트 값 | 약 4,281개(정제 후, 약 53%가 유일값) |
| 숫자 비중 | 약 60.5% |
| 문자 집합 | 숫자 0-9 + 대문자 A-Z + 기호(- / . ·) |

### 데이터 성격
- 도메인이 좁고 일관됨: `8196 P32 E33S`, `8129 11C B3601114 H1B`, `H32C-52` 형태의 **영숫자 코드**가 지배적.
- 구조 규칙성 존재: `숫자4자리 + P/E/H 계열 코드 + 하이픈/슬래시 구분자`의 반복 문법.
- 정제 완료 항목: 한자·전각문자·이질기호(`"` `"` `、`)는 제거됨. 소문자 오염은 80건 → **3건**으로 감소(원본 대조 결과 실제 소문자로 확정. 문자 사전은 대문자 정규화로 확정했으므로 이 3건은 학습·평가 시 대문자로 정규화 — 2장·Phase 1·3 참조). 중점(`·`)은 유효 구분자로 유지.
- **레이블링 포인트 혼재**: 4점 사각형 8,004건(98.8%)과 5점 이상 다각형 99건(1.2%)이 공존. 다각형은 곡면 인쇄 텍스트이며 실사용 대상 → 상세는 5장 참조.

### 단위 정의 (문서 전체 공통) — *신규*
곡면 표본이 절마다 "99"와 "93"으로 혼용되던 문제를 다음으로 고정한다.
- **박스(box) 단위 = 99**: 다각형 텍스트 박스의 수. 오버샘플링·박스 단위 평가·시퀀스 통계는 이 값을 쓴다.
- **이미지(image) 단위 = 93**: 다각형 박스가 존재하는 원본 이미지의 수. 데이터 분할(train/val/test)은 **반드시 이미지 단위**로 수행한다(누수 방지).
- 이하 모든 절은 "곡면 박스 99 / 곡면 이미지 93"로 표기를 통일한다.

## 2. 데이터 진단 요약 (Fine-tuning 관점)

### 유리한 요소
1. **좁은 도메인 / 고정 문자셋** — 학습 클래스가 제한적이어서 빠른 수렴 기대.
2. **충분한 표본** — 8,000개 이상 박스, 핵심 코드(`8166`, `8196`, `E51S` 등) 반복 → 강한 학습 신호.
3. **구조적 문법** — 모델이 코드 사전확률(prior)을 학습해 부분 오인식을 보정할 여지.

### 남은 위험 요소 (해결 대상)
| 위험 | 내용 | 영향 규모(추정) | 영향 |
|---|---|---|---|
| ~~혼동 문자 라벨 불일치~~ **(해소 완료)** | 초기 48개 그룹에서 1↔I, 5↔S, 0↔O, 8↔B 혼동 존재 → 반복 정제(48→23→14→최종)로 **전원 원본 이미지 대조·수정 완료**. 자동 탐지에 남은 12개 표기쌍(`8135`/`B13S`, `83`/`B3`, `205`/`20S`, `(5)`/`(S)`, `8165`/`B16S` 등)은 **오기가 아니라 실존하는 별개 부품 코드로 확정** | 잔여 0건(실존 코드) | 해소됨. 정제 이력은 7장·Phase 1 기록으로 보존 |
| 박스 분할 불일치 | 공백 포함 다중 토큰 박스 21.6% (`8196 P32` vs `8196`+`P32`) — *전체 8,103박스 모집단 기준* | 약 1,750박스 | detection/recognition 기준 흔들림 |
| 잔여 소문자 라벨 | `166m84`, `Nav-D`, `E27C. 50X50X6t` — **실제 소문자 3건 확정** | 3건 | 대문자 정규화로 흡수, 소문자 원값은 이력 보존(Phase 1-2, 3-2) |
| 긴 코드 희소성 | 길이 15자 이상 복합 코드 대부분 유일값 | 유일값 다수 | 일반화 곤란 |
| 시각적 혼동 문자 집중 (라벨 정제와 별개) | O/0, I/1, S/5, B/8, Z/2가 코드 전반에 다수 → 라벨은 정제됐어도 **추론 시 저해상도·마모에서 오인식 소지**는 상존 | 전반 | 학습 단계 이슈. 후단 DB 매칭·class-weighted loss로 관리 |
| **데이터 누수(신규)** | 핵심 코드가 여러 이미지에 반복 → 이미지 단위 분할로도 **동일 시리얼 값이 train/test 양쪽 노출** | — | test 성능 과대평가 |

> **모집단 주의**: "박스 분할 불일치 21.6%"는 전체 8,103박스 기준, "곡면 다중 토큰 69%"(5장)는 곡면 99박스 기준이다. 두 통계는 모집단이 다르므로 병렬 비교하지 않는다.

## 3. 목표 및 성공 지표

### 목표
범용 OCR 대비 이 라벨 도메인에서 인식 정확도를 향상하되, **최종 목표는 "정답 시리얼을 현장 화면 후보에 띄우는 것"**으로 설정한다. 상용 배포 시 부품 시리얼 번호 DB와 매칭해 글자 매칭률이 높은 후보를 화면에 제시·선택하는 구조이므로, 모델이 코드를 완벽히 맞히지 못해도 후단 매칭이 오류 상당수를 흡수한다.

### 3.1 KPI 계층 분리 — *구조 개편*
리뷰 지적을 반영해 **OCR 모델 KPI**와 **시스템 KPI**를 명확히 분리한다. Top-K는 OCR 단독 성능이 아니라 `OCR + DB Search + Ranking` 전체의 지표이므로 시스템 계층에 둔다.

**[모델 KPI] — 이 문서(fine-tuning)가 직접 책임지는 지표**
1. **Character-level Accuracy (CAR)** — 정규화 편집거리 기반(1 − normalized edit distance). 삽입·삭제·치환 일관 반영, 긴 코드 문자 누락 왜곡 방지. **주 모니터링 지표.**
2. **Exact-match Rate** — 순수 모델 성능 기준선. 후단 없는 상태의 하한 감시용.
3. **혼동 문자 클래스별 오인식률** — 0/O, 1/I, 5/S, 8/B, 2/Z 혼동 행렬. 위치별(앞자리/끝자리) 오류 분해. **이 축들은 오기가 아니라 실존 코드를 가르는 구별축**(`8135`/`B13S` 등 확정)이므로, 오인식은 곧 다른 실존 부품으로의 오분류를 의미 → 최우선 감시.

**[시스템 KPI] — 후단 매칭을 포함한 상용 목표 지표**
4. **Top-K Retrieval Accuracy** — 예측 코드로 시리얼 DB 조회 시 정답이 상위 K개(K=3~5) 후보에 드는 비율. **단, 아래 3.2의 DB 프록시·매칭 함수가 정의되어야 측정 가능.**
5. **Top-1 Retrieval Accuracy(신규·필수)** — 정답이 **1위**인 비율을 별도 추적. Top-K는 "틀린 유효 시리얼(`E501`→`E503`)이 정답보다 위에 오는" 실패를 감점하지 못하므로, 편집거리 1 쌍의 오답 상위 노출을 Top-1로 감시한다.
6. **매칭 신뢰도 임계값 / 미등록 판정** — 폐집합 이탈(신규·미등록 부품)에서 틀린 후보 강제 제시를 막는 "후보 없음/신뢰도 낮음" 판단 임계값.

### 3.2 평가용 DB·매칭 프록시 정의 — *신규(A-2 해소), 단계 분리 반영*
Top-K/Top-1이 "측정 방법 없는 지표"가 되지 않도록, **상용 인프라와 별개로 이 문서 안에 평가용 baseline을 고정**한다. 단, 아래 항목은 **"즉시 정의할 것"과 "인식 모델 확정 후 튜닝할 것"으로 나뉜다** — 신뢰도 기반 튜닝은 실제 모델 출력 분포 없이는 추측에 불과하기 때문이다(실행 순서는 `claude_code_prompt_paddleocr_colab.md` TASK 3 / TASK 6-E 참조).

**[즉시 정의 — 실행 문서 TASK 3]**
- **DB 프록시 구성**: 학습 데이터의 고유 시리얼 값 약 4,281개(정제 후 기준) + (확보 시) 부품 마스터 목록을 합집합해 **평가용 시리얼 사전**을 구성. 스냅샷 버전 태그를 붙여 고정(예: `serial_db_proxy_v1`).
- **폐집합/개집합 명시**: 1차 평가는 **폐집합**(정답이 반드시 DB에 존재)으로 상한을 측정하고, 2차로 미등록 N%를 섞어 **개집합** 성능(임계값 동작)을 측정.
- **기본 매칭 함수**: **정규화 편집거리(Levenshtein) 기반 Top-K 랭킹**을 baseline으로 고정. **금지: 문자 골격 정규화(8↔B, 5↔S, 0↔O, 1↔I, 2↔Z 접기)를 매칭 함수에 넣지 않는다** — `8135`와 `B13S`가 둘 다 실존 코드로 확정되었으므로, 이들을 접으면 서로를 오답 후보로 강제 매칭시켜 Top-1이 붕괴한다.
- **후보 공간 크기 기록**: DB 규모(|DB|)를 함께 리포트. K=5의 난이도는 후보 공간 크기에 종속되므로, |DB|가 바뀌면 Top-K 수치를 직접 비교하지 않는다.
- **예측 원본 아카이빙 규칙(신규)**: baseline·fine-tuned 추론 시 **텍스트 예측값 + 문자별 확신도(logit/softmax)를 원본 그대로 저장**한다. 이렇게 하면 아래 신뢰도 튜닝이 나중에 완성돼도 baseline·fine-tuned 양쪽에 소급 적용해 Top-K를 재계산할 수 있다 — "매칭 튜닝은 나중에 완성한다"와 "baseline부터 Top-K를 잰다"가 충돌하지 않는 이유.

**[인식 모델 확정 후 튜닝 — 실행 문서 TASK 6-E]**
- **신뢰도 가중 동점 처리**: 편집거리가 동일한 후보가 여럿이면 인식기의 문자별 확신도로 가중해 순위를 정한다. 이 가중은 **동일 편집거리 후보 간 순위 조정**에만 쓰이며, 문자를 병합(위 금지 규칙)하는 것과는 다르다.
- **미등록 판정 임계값 튜닝**: 실제 모델의 확신도 분포를 보고 "후보 없음/신뢰도 낮음" 임계값을 실측 기반으로 설정.
- 필요 시 n-gram/가중 편집거리를 비교군으로 추가하되, **동일 매칭 함수·동일 DB 스냅샷에서만 학습 간 비교**한다.

### 3.3 정량 목표선 — *신규(B-2 해소)*
"유의미하게 향상" 같은 상대어를 제거하고, **Phase 4 반복의 종료 조건**을 정의한다. 아래는 초기 목표선이며, Phase 0에서 baseline을 실측한 뒤 확정한다.

| 지표 | Baseline(범용 OCR, **Phase 0에서 실측**) | 목표선(초안) |
|---|---|---|
| CAR | 측정값 기입 | ≥ baseline +N%p (실측 후 확정) |
| Top-K@5 (폐집합) | 측정값 기입 | ≥ 95% (|DB| 확정 후 재보정 — 3.2 후보 공간 종속성) |
| Top-1 (폐집합) | 측정값 기입 | ≥ 85% (초안) |
| 곡면 서브셋 Exact-match | 측정값 기입 | 하락 없음(회귀 방지) |

> **Exit Criteria(신규)**: 목표선 미달 시 오답 유형(3.1-3)을 Phase 1로 피드백해 재학습. 목표선 도달 또는 3회 반복 내 개선폭 <1%p면 종료하고 결과를 리포트. **반복 후에도 목표 미달이면 재학습을 무한 반복하지 말고 Fallback 매트릭스(6장, F1~F7)로 전환** — 특히 곡면·검출·Top-K가 기술적으로 더 개선되지 않을 때는 자동화 스코프 축소·수동 개입 경로 같은 비즈니스 레벨 대응으로 넘어간다.

## 4. 실행 단계 (권장 순서)

### Phase 0 — 영향 규모 산정 및 Baseline 측정 *(신규 선행 게이트)*
후속 단계의 우선순위와 목표선을 정하기 위해 실제 규모와 출발점을 먼저 확정한다.

- **착수 전제**: baseline 실측에는 최소한의 평가 실행 환경(추론용 GPU·평가 스크립트)이 필요하다. 상세 리소스 산정은 `Training_Strategy.md`로 이관하되, Phase 0 착수 시점에 평가 환경만은 확보되어 있어야 한다.

1. ~~**혼동 문자 48그룹의 영향 박스 수 산정**~~ **(완료)** — 원본 이미지 대조·수정을 완료했으므로 별도 영향 산정은 불필요. 잔여 표기쌍 12개는 실존 별개 코드로 확정(1장·2장 참조). Baseline 측정만 진행한다.
2. **Baseline 실측** — 범용 OCR로 CAR·Top-K·Top-1을 3.2 프록시 기준으로 측정해 3.3 표를 채운다.
3. **곡면 복합 표본 집계** — "곡면 × 다중 토큰 × 긴 코드"가 겹친 실사 표본이 곡면 99박스 중 몇 건인지 집계(5장 D 항목과 연결).

### Phase 1 — 라벨 정제 (Fine-tuning 전 필수 선행)
가장 큰 병목이었다. 이 단계 완료도가 최종 성능 상한을 결정한다. **Phase 1은 합성 증강(Phase 2)의 논리적 선행이다** — 정답 문자셋·혼동 문자가 확정되지 않으면 합성 문법 파라미터가 오염된 채 정의되기 때문(A-1). **혼동 문자·소문자 정제는 완료됐고, 남은 항목은 박스 분할 표준화다.**

1. **혼동 문자 그룹 통일 — 완료**
   - 자동 탐지(I/1, O/0, S/5, B/8, Z/2 정규화 후 충돌 그룹 추출)로 초기 48개 그룹 식별.
   - **원본 이미지 대조·수정 완료**: 반복 정제로 48→23→14→최종까지 축소. 오기는 정답 1개로 통일 완료.
   - **잔여 표기쌍 12개는 실존하는 별개 부품 코드로 확정**(`8135`/`B13S`, `83`/`B3`, `205`/`20S`, `(5)`/`(S)`, `8165`/`B16S`, `501`/`S01`, `925`/`92S`, `P1`/`PI`, `L85`/`LB5`, `628`/`6Z8`, `165`/`16S`, `ST035`/`ST03S`). 이들은 통일 대상이 아니며, 서로 다른 코드로 유지한다. 특히 **`숫자` vs `문자+숫자` 형태(`8135`↔`B13S`, `83`↔`B3` 등)가 둘 다 실존함이 원본 이미지로 확정**되었다 — 즉 이 도메인에서 `8`/`B`, `5`/`S`, `2`/`Z`, `0`/`O`, `1`/`I`는 단순 오기가 아니라 **의미가 다른 문자로 반드시 구별해야 하는 축**이다.
   - **정규화 정책에의 함의(중요)**: 위 사실은 문자 골격 정규화(skeleton normalization)를 라벨·평가 파이프라인에 적용하면 **안 됨**을 뜻한다. `8135`와 `B13S`를 같은 것으로 접으면 실존 코드 2개가 붕괴한다. 자동 탐지에 썼던 8↔B·5↔S 정규화는 *오기 후보를 찾기 위한 탐지용*일 뿐, **정답·매칭 기준으로는 원문자를 엄격히 구분**한다(이는 대문자 정규화(Phase 3-2)와 무관 — 대문자 정규화는 대소문자 축만 접고, 0/O·1/I·5/S·8/B·2/Z 문자 정체성은 보존한다).
   - **후속 유의점**: 이 12쌍은 시각적으로 1글자만 다른 실존 코드이므로, DB 매칭 단계에서 서로 최상위 오답으로 뜰 수 있다 → Top-1 지표(3.1)와 혼동 행렬(4-1)로 상시 감시. 인식기 학습 시 이 문자쌍에 **class-weighted loss/hard example mining을 집중 적용**(Phase 3-3)한다.
2. **잔여 소문자 라벨 3건** (`166m84`, `Nav-D`, `E27C. 50X50X6t`) — 원본 대조 결과 **실제 소문자로 확정**(오기 아님). 문자 사전은 대문자 정규화(Phase 3-2)로 확정했으므로, 이 3건은 **학습·평가 시 대문자로 정규화**하고 소문자 원값은 라벨 파일에 이력으로만 보존한다. 별도의 정규화 "예외 클래스"를 두지 않는다(예외를 두면 사전에 소문자를 부분 도입하는 셈이 되어 C-2 결정과 상충).
3. **박스 분할 기준 통일**
   - 규칙 결정: 공백으로 구분된 인접 코드를 (a) 한 박스로 병합할지 (b) 개별 박스로 분리할지 프로젝트 표준 확정.
   - 권장: 물리적으로 한 줄에 인쇄된 코드군은 한 박스 유지하되, 학습 시 후처리로 토큰 분리. **단, 이 방식의 공백 실패 모드는 5장 5항의 대응책과 함께 검토**(C-3).

#### 라벨 승인 프로세스 *(신규 — Label Noise 기준)*
혼동 문자·소문자·박스 분할 판정의 재현성을 위해 승인 체인을 고정한다.
```
Annotator(원본 대조 1차 판정)
   → Reviewer(그룹별 교차 검증)
   → Final Approval(표준 확정 + 사유 기록)
```
각 판정은 `그룹 ID / 원본 이미지 참조 / 확정값 / 판정 사유 / 승인자`를 로그로 남긴다.

### Phase 2 — 데이터 분할 및 증강
1. **Train/Val/Test 분할** (예: 80/10/10) — **누수 방지 규칙(신규)**:
   - **이미지 단위 분할**을 기본으로 하되, 핵심 코드가 여러 이미지에 반복되므로 **시리얼 값 단위 그룹 분할(Group/Product Split)**을 병행. 즉 **동일 시리얼 값이 train과 test에 동시 등장하지 않도록** 값 기준으로 그룹을 묶어 분할한다.
   - **DB 프록시와의 연결(주의)**: 고유값이 53%라 그룹 분할 시 test에만 존재하는 시리얼이 다수 생긴다(일반화 측정에는 정직함). 단, 폐집합 Top-K 평가가 성립하려면 **그룹 분할로 학습에서 제외된 시리얼도 DB 프록시(3.2, `serial_db_proxy_v1`)에는 반드시 포함**해야 한다. "학습에서 뺀다 ≠ DB에서 뺀다"를 구분한다.
   - 분할 시드를 고정하고 기록(재현성, 8장).
2. **곡면 분할·검증셋 — 충돌 해소(신규, B-1)**
   - 곡면 이미지 93개를 **train/val/test에 층화 분할**로 비례 배분(train에 실제 곡면이 0이 되는 것을 방지).
   - **곡면 검증셋은 "93개 전량 고정"이 아니라 "test에 배분된 곡면 서브셋을 고정"**한다. 매 학습 이 고정 서브셋으로 동일 기준 비교. (기존 문서의 "93 전량 검증셋 고정" ↔ "층화 분할" 모순을 이 규칙으로 해소.)
3. **합성 데이터 증강 (데이터 부족 대응책 중 최우선 — 범위 한정)**
   - 표기 수정: "최우선 선행 작업"이 아니라 **"Phase 1 완료를 전제로 한, 데이터 부족 대응책 중 최우선"**(A-1). 성패의 논리적 선행은 Phase 1이다.
   - 코드 문법(`숫자4자리 + 문자코드 + 구분자 + H1B` 등)을 파라미터화해 미등장 유효 조합까지 커버. 혼동 문자·희소 문자·긴 코드가 충분히 등장하도록 분포 균형화.
   - 도메인 폰트 + 실제 배경 텍스처 + 곡면 왜곡(5장) 결합.
   - **합성 검증 게이트(신규, C-1)**: 합성은 "만능 해결책"이 아니다. 반드시 아래를 측정해 채택 여부 결정.
     - `실사만 학습` vs `실사+합성 학습`을 **실사 검증셋에서 성능 비교**.
     - **합성:실사 비율을 하이퍼파라미터로 스윕**(예: 1:1, 3:1, 5:1)하고 실사 검증 성능이 꺾이는 지점 감시.
     - 합성 곡면 rectification 학습 시 **합성 곡률 과적합**을 실사 곡면 서브셋으로 회귀 감시.
4. **일반 증강 — 확장(신규, 리뷰 반영)**
   > 합성 데이터(3항)는 "코드 어휘·곡면 다양성"을 늘리는 것이고, 이 항목은 **실제 카메라 촬영 조건의 다양성**을 늘리는 것으로 목적이 다르다. 산업 현장 배포를 전제로 한 이 프로젝트에서는 이 증강이 문자 인식 자체만큼 중요할 수 있다는 지적을 반영한다.
   - **표준 증강**: 회전, 밝기/대비, 블러, 노이즈, 원근 왜곡.
   - **도메인 특화 증강(신규)**: Specular/Metal Reflection(금속 반사), Rust(녹), Scratch(스크래치), Oil(기름), Dust(먼지), Motion Blur(손떨림), Compression(압축 아티팩트). 표준 라이브러리에 없어 별도 구현 필요(실행 세부는 `claude_code_prompt_paddleocr_colab.md` TASK 5-B).
   - **[게이트] 배포 맥락 검증**: 위 항목을 무분별하게 다 넣지 않는다. 신품 부품(공장 출고 직후)인지 사용 중/야외 보관 부품(마모·오염 노출)인지에 따라 관련 항목이 달라지므로, 항목별로 실사 검증셋에서 효과를 비교해 개선을 주는 것만 채택한다(불필요한 증강은 학습 신호를 흐릴 뿐 효과가 없다). 합성 검증 게이트(3항 C-1)와 동일한 원칙.

### Phase 3 — 모델 및 학습
*(세부 아키텍처는 `claude_code_prompt_paddleocr_colab.md`로 이관됨. 여기서는 최종 확정된 결정과 그 근거만 기록한다.)*

1. **모델 확정 — PaddleOCR 기준 실제 채택 조합(수정)**
   - **검출**: PP-OCRv5 server det(DBNet 계열) 하나로 확정. DBNet은 폴리곤 출력을 지원해 곡면·회전 텍스트에 대응.
   - **인식**: RARE/StarNet(TPS rectification 내장, PaddleOCR v2.0 dygraph 세대 — 사전학습 가중치 URL 확인됨) vs SVTR/PP-OCRv5 rec(TPS 미내장, 최신·고정확 backbone) 중 **실측 비교로 채택**. 애초 후보로 검토했던 FCENet/PSENet/TextSnake(검출), ASTER/PARSeq(인식)는 실제 PaddleOCR 구현 검증 과정에서 위 조합으로 좁혀졌다.
   - **[게이트] 검출 fine-tuning은 조건부다(신규 — 리뷰 반영)**: 검출을 무조건 fine-tuning 대상으로 전제하지 않는다. baseline을 **평면(4점, 98.8%) / 곡면(1.2%) 서브셋으로 나눠 recall/precision을 측정**하고, 평면이 임계값(예: 95%) 이상이면 검출 fine-tuning을 생략하고 사전학습 검출기를 그대로 사용한다(리소스는 인식 fine-tuning에 우선 배분 — 이 프로젝트의 핵심 병목은 검출이 아니라 혼동 문자·긴 코드 인식). 곡면만 유독 낮으면 전체 재학습이 아니라 곡면 증강 데이터만으로 저비용 이어학습을 우선 검토한다.
2. **문자 사전(dictionary) 정책 — 대문자 정규화로 확정(C-2)**
   - **확정: 대문자 정규화.** 문자 사전은 숫자 0-9 + 대문자 A-Z + 기호(- / . · 공백)로 구성하고 소문자 a-z는 사전에 포함하지 않는다. 근거: 실제 소문자가 3건에 불과한데 a-z 26자를 전부 열면 o/O·s/S·c/C 대소문자 혼동축이 새로 생겨, 이 도메인 최대 위험(0/O·1/I·5/S)에 혼동 공간을 더한다. 이득(3건) 대비 비용(혼동 클래스 26개 추가)이 불균형하다.
   - **실사 소문자 3건 처리(Phase 1-2)**: 실제 소문자로 확정된 3건(`166m84`의 `m`, `Nav-D`의 `v`, `E27C. 50X50X6t`의 `t`)은 **학습·인식 파이프라인에서 대문자로 정규화**한다(모델은 대문자만 출력). 원본 라벨 파일에는 소문자 원값을 아카이브로 남기되, 학습 타깃·예측·평가 비교는 모두 대문자 기준으로 수행한다(즉 정규화가 정답 기준이며, 소문자 원값은 이력 보존 목적일 뿐 학습에 사용하지 않는다). DB 매칭 단계도 대소문자 무시(case-insensitive) 비교로 통일.
   - **향후 재검토 조건**: 운영 중 소문자 코드가 유의미하게 유입되면 a-z 포함을 재검토하고, 채택 시 대소문자 혼동률을 3.1-3 지표에 추가한다.
3. **학습 전략 — 단계화 원칙(신규, "한 번에 한 변수만")**
   > 리뷰 반영: 검출·인식 백본 선택·합성·TPS·매칭 튜닝을 한 실험에 몰아넣으면 문제 발생 시 원인을 특정할 수 없다. **매 단계는 이전 단계의 체크포인트 위에 변수 하나만 추가**하고, 추가 전/후를 실사 검증셋에서 비교해 순효과를 분리 측정한다(실행 세부는 `claude_code_prompt_paddleocr_colab.md` TASK 6 참조).

   | 단계 | 내용 | 비교 기준 |
   |---|---|---|
   | 1. 인식 기본기 | SVTR(TPS 없음), 실사만, 혼동 문자 가중 | baseline 대비 |
   | 2. 검출(조건부) | 위 1-[게이트] 판단 시에만 DBNet fine-tuning | 1단계 대비 |
   | 3. 합성 | 합성 데이터 배합비 스윕(Phase 2-3) | 1단계 대비 순효과 |
   | 4. TPS/곡면 업그레이드 | RARE로 교체 실험(TPS freeze→점진 unfreeze) | 3단계 대비 곡면 개선 여부 |
   | 5. 매칭 튜닝 | 신뢰도 가중·임계값(3.2 하단) | 4단계 최종 모델 기준 |

   - 4단계를 3단계 뒤에 두는 이유: 3단계까지 SVTR 기준선이 이미 확정돼 있어야 "TPS 교체가 실제로 이득인가"를 깨끗하게 비교할 수 있다.
   - 혼동 문자에 class-weighted loss 또는 hard example mining은 곡면·합성과 무관하게 항상 유효하므로 1단계부터 적용한다.
   - 인식기 언어모델 헤드로 코드 문법 prior 학습.

### Phase 4 — 평가 및 반복
1. **혼동 행렬 분석** — 0/O, 1/I, 5/S, 8/B, 2/Z 오인식 집중 여부.
2. **곡면/평면 분리 평가** — 곡면 고정 서브셋(Phase 2-2)의 Exact-match를 **진단 보조 지표**로 추적. 통합 지표에 묻히지 않도록 분리하되, 주 목표는 여전히 시스템 KPI(Top-K/Top-1)임을 명시(A-3 해소: 곡면 Exact-match는 "후단이 흡수 못 하는 케이스 감시용" 진단 지표).
3. **오답 유형 분류** — (a) 검출 실패 (b) 인식 오류 (c) 라벨 오류를 구분해 Phase 1로 피드백.
4. **공백 경계 오류율 추적(신규, C-3)** — 다중 토큰 통째 인식 시 공백 위치 오인식률을 별도 측정. 곡면 69% 다중 토큰이 여기서 무너지면 DB 매칭이 직접 실패하므로 상시 감시.
5. **반복 개선** — Exit Criteria(3.3)에 따라 종료 판단.

## 5. 곡면 텍스트 대응 (실사용 대상 확정)

### 배경
레이블링 포인트가 4개(사각형)인 박스와 5개 이상(다각형)인 박스가 혼재한다. 다각형은 파이프·원통 등 **곡면에 인쇄된 텍스트**이며, **이 프로젝트의 실사용 인식 대상으로 확정**되었다.

### 곡면 데이터 실태
| 유형 | 박스 수 | 이미지 수 | 비중(박스) |
|---|---|---|---|
| 4점 (사각형/평면) | 8,004 | — | 98.8% |
| 5점 이상 (다각형/곡면) | 99 | 93 | 1.2% |

- 곡면 라벨은 평균 13.9자, 절반 이상이 20자 이상인 긴 복합 코드(`8128 D81C 1K 221-201 H1B` 등).
- 곡면 라벨의 **69%가 공백 포함 다중 토큰**(곡면 99박스 모집단 기준).
- 곡면 난이도 + 긴 코드 난이도가 같은 샘플에 겹침 → 실사용상 가장 중요한 전체 부품 코드를 놓칠 위험.

> **실사 표본 확인 필요(신규, D)**: "곡면 × 다중 토큰 × 긴 코드"가 겹친 실사 표본이 99박스 중 실제 몇 건인지 Phase 0에서 집계한다. 이 값이 rectification 학습 신호의 실질 규모다.

### 설계 지침
1. **검출: 폴리곤/곡선 텍스트 검출기 채택(필수)** — DBNet++, FCENet, PSENet, TextSnake 등 임의 형상 검출기. 기존 다각형 애노테이션 활용.
2. **인식: 곡면 보정(rectification) 내장 인식기** — TPS rectification 내장 STR(ASTER, TPS+BiLSTM+Attention, SVTR·PARSeq). 긴 코드 대응에 attention 디코더가 CTC 단독보다 유리. (학습 전략은 Phase 3-3.)
3. **폴리곤 전처리 표준화** — (a) 점 순서 정규화(시계 방향, 좌상단 시작), (b) 상단선/하단선 분리 후 TPS 제어점 매핑, (c) 자기교차 검증을 파이프라인에 고정.
   - **[게이트] 표준 라이브러리로 처리 불가 — 직접 구현 필수(신규, 실측 확인)**: PaddleOCR의 표준 크롭 함수(`get_rotate_crop_image`)는 4점 입력만 지원하며, 5점 이상 폴리곤을 넣으면 예외가 발생함을 실제 사례(GitHub Issue #5300, 곡면 검출 결과를 그대로 입력했다가 크래시)로 확인했다. 곡면 99박스는 segment-based unrolling(권장) 또는 최소외접사각형 폴백(대안, TPS 보정에 위임)으로 별도 구현하고, 이 구현 검증을 선행 게이트로 둔다(실행 세부는 `claude_code_prompt_paddleocr_colab.md` TASK 1).
4. **곡면 샘플 희소성 대응 — 과적합 감시 병기(신규)**
   - 곡면 왜곡 합성 증강(평면 8,004건에 원통/아치 warping) + 실제 99박스 오버샘플링.
   - **과적합 감시**: 오버샘플링은 99박스의 특정 코드·배경에 과적합될 수 있으므로, 실사 곡면 서브셋을 held-out으로 두고 회귀 감시(C-1).
   - **표본 부족 대응**: 곡면이 절대 부족(99박스)하므로 곡면 전용 평가는 단일 분할 대신 **K-Fold 교차검증**을 병행해 평가 분산을 줄인다(리뷰2-#8).
5. **긴 코드 × 곡면 복합 난이도** — 인식기 최대 시퀀스 길이를 실측 최댓값(24자+ 여유) 이상으로. 다중 토큰은 통째 인식 후 후처리 분리하되, **공백 경계 오류율(Phase 4-4)을 필수 감시**하고 임계 초과 시 토큰 분할 검출 방식을 대안으로 재검토(C-3).
6. **평가: 곡면/평면 분리 측정(필수)** — Phase 2-2에서 고정한 곡면 서브셋으로 매 학습 동일 기준 비교. 곡면 Exact-match는 진단 보조 지표(3.1, 4-2).
7. **데이터 분할: 층화 분할** — Phase 2-2 규칙을 따른다(93 전량 고정과 층화 분할의 충돌은 그곳에서 해소).

### 곡면 대응 종합
파이프라인 정답 조합은 **DBNet(폴리곤 검출) + RARE/SVTR 중 실측 채택(3장 Phase 3-1 참조)**. 최대 리스크는 곡면 99박스의 희소성과 긴 코드의 겹침이며, **합성 증강(검증 게이트 적용) + 층화 분할 + 곡면 분리 평가 + 과적합/공백 감시**로 관리한다.

### 6.1 Fallback 매트릭스 — 트리거 조건과 구체적 대응 (신규, 리뷰 반영)
> 위 표는 "무엇을 감시하는가"까지만 정의한다. 리뷰에서 "측정 결과가 나쁠 때 무엇을 할지가 없다"는 지적을 받아, 주요 실패 지점마다 **트리거 조건 + 구체적 대응 행동**을 짝지운다. 실행 세부는 `claude_code_prompt_paddleocr_colab.md`의 F1~F7 매트릭스를 참조하고, 여기서는 fine-tuning 실패가 **비즈니스 레벨 대응으로 넘어가는 지점**만 요약한다.

| 실패 시나리오 | 트리거 | 대응 |
|---|---|---|
| TPS(RARE) 실패 | 곡면 검증셋에서 SVTR 기준선보다 낮음 | SVTR 체크포인트로 롤백, 곡면은 폴리곤 크롭 정규화에만 의존 |
| 인식 기본기 자체가 부진 | 1단계 완료 시점에 baseline 대비 개선 없음 | 이후 단계(검출·합성·TPS) 착수 전에 원인 해결 — 경량 backbone 교체, 크롭 품질 재점검 |
| 합성 데이터 전면 실패 | 모든 배합비에서 실사 대비 악화 | 합성 폐기, 실사 추가 수집으로 전환, 원인 진단 리포트 보존 |
| **곡면 성능이 끝까지 목표 미달** | 위 대응을 다 거쳐도 곡면 지표가 목표선 미도달 | **비즈니스 레벨 폴백**: 자동 매칭에 바로 태우지 않고 저신뢰 곡면 예측은 "수동 확인 필요"로 현장 UI에 플래그(Human-in-the-loop). 자동화 스코프를 평면으로 한정하고 곡면은 별도 로드맵으로 이연 |
| **검출 fine-tuning을 해도 목표 미달** | fine-tuning 후에도 recall/precision 임계 미달 | DB 후처리 파라미터 우선 튜닝 → 다른 검출 아키텍처 비교 → 최종적으로 **사용자 수동 ROI 지정**(검출 우회) |
| **Top-K 매칭 목표 미달** | 최종 평가에서 시스템 KPI 미도달 | 후보 개수 K 확대, 매칭 UI에 수동 검색 폴백 추가, 저신뢰 예측은 원문 그대로 표시 |

**운영 원칙**: 각 Fallback 발동 시 트리거 조건·시각·선택한 대응·근거를 기록한다(7장 재현성 원칙과 동일 이유).

## 8. 결론
정제 작업으로 문자셋 오염이 거의 해소되고 **혼동 문자 라벨 불일치까지 원본 이미지 대조·수정이 완료**되어, 최대 병목이 제거됐다. 남은 결정적 게이트는 **Phase 1의 박스 분할 표준화**이며, 이것이 Phase 2 합성 증강의 논리적 선행이다. 혼동 문자 정제 결과 남은 12개 표기쌍은 오기가 아니라 실존하는 별개 부품 코드로 확정됐으므로, 통일하지 않고 유지하되 1글자 차 실존 코드가 매칭 단계에서 오답 상위로 뜨지 않는지 Top-1 지표로 감시한다.

본 수정본의 핵심 변경은 네 가지다. 첫째, **주 KPI(Top-K)를 측정 가능하게** 만드는 DB·매칭 프록시와 정량 목표선을 이 문서 안에 정의했다(3.2·3.3). 둘째, **곡면 검증셋 고정과 층화 분할의 충돌**을 "test 배분 서브셋 고정" 규칙으로 해소했다(Phase 2-2). 셋째, **데이터 누수·합성 역효과·공백 경계 오류**라는 세 실패 모드에 감시 지표를 붙였다. 넷째, **재현성 장**을 신설했다.

곡면 텍스트가 실사용 대상으로 확정된 만큼 폴리곤 검출기 + rectification 내장 인식기로 설계하되, 곡면 희소성을 합성 증강(검증 게이트)·층화 분할·분리 평가·과적합 감시로 관리한다. 평면 정확도만 높고 곡면을 놓치는 결과를 막는 것이 두 번째 성패 요인이다.

> **추가 확정 사항(이번 정리)**: ① 문자 사전은 **대문자 정규화로 최종 확정**(소문자 a-z 미포함) — 실사 소문자 3건은 대문자로 정규화하고 원값은 이력 보존, 정규화 예외 클래스는 두지 않음. ② Top-K 목표선은 |DB| 확정 후 재보정. ③ 그룹 분할로 학습에서 제외된 시리얼도 DB 프록시에는 포함(폐집합 평가 성립 조건). ④ Phase 0 착수 전제로 평가 환경 확보를 명시.
>
> **상태 갱신**: **혼동 문자 라벨 정제 완료**(48→최종, 원본 이미지 전수 대조). 잔여 12개 표기쌍은 실존 별개 코드로 확정 → Phase 0의 영향 산정 항목 종료, 남은 정제 게이트는 박스 분할 표준화만 남음.

> **본 개정(실행 문서 동기화)**: `claude_code_prompt_paddleocr_colab.md`가 여러 차례 리뷰를 거치며 앞서간 결정사항을 본 문서에 소급 반영했다. ① 모델 후보를 실제 채택 조합(DBNet/RARE·SVTR)으로 교정, ② 검출 fine-tuning을 조건부 게이트로 전환, ③ 학습 전략을 "한 번에 한 변수만" 5단계 원칙으로 재구성, ④ 3.2를 즉시 정의(TASK 3) vs 인식 확정 후 튜닝(TASK 6-E)으로 분리 + 예측 아카이빙 규칙 추가, ⑤ 일반 증강에 산업 현장 도메인 특화 열화(반사·녹·스크래치 등) 추가, ⑥ 곡면 크롭이 표준 라이브러리로 불가능함을 실측 확인해 게이트로 반영, ⑦ Fallback 매트릭스(6.1)로 "실패 시 무엇을 할지"의 공백을 메움. **아울러 `System_Architecture.md`를 신설**해 현장 앱 개발에 재사용 가능한 결정(시스템 KPI의 UX 함의, 매칭 서비스 설계, 문자 골격 정규화 규칙, Fallback의 저하 모드 UX)을 이관했다.

## 2. 🔴 발견 — DB에 공백만 다른 중복이 99군집 있었다

매칭 함수는 지시서 TASK 3-2 지침에 따라 **공백을 무시**한다. 그런데 라벨에는
같은 코드가 공백만 다르게 표기된 경우가 다수 있었다:

```
' 8196 LUM 02'  '8196 LUM 02'  '8196 LUM02'  '8196LUM 02'  '8196LUM02'
'EA 8049 P4C-04'  'EA 8049P4C-04'  'EA8049 P4C-04'  'EA8049P4C-04'
'(1) D11C'  '(1)D11C'
```

군집 99개 / 시리얼 207개 (크기 분포: 2개 93군집, 3개 4, 4개 1, 5개 1).

### 왜 문제인가
공백 무시 비교에서 이들은 **거리 0으로 서로 구별 불가능**하다. DB에 남겨두면
Top-1 이 동점 후보 중 임의로 하나를 골라 **모델 성능과 무관하게 최대 4.8%(207/4,279)
까지 깎인다.** 이것은 측정 오류이지 성능이 아니다. 실제 부품 마스터라면 한 부품에
5가지 표기가 있을 리도 없다.

실제로 이 문제는 테스트 실패로 드러났다 — DB 시리얼을 자기 자신으로 조회했는데
Top-1 정확도가 100%가 아니라 95%였다(`'(1)D11C'` 가 `'(1) D11C'` 에 밀림).

### 조치
공백 제거형을 키로 병합하고, **대표 표기는 라벨에서 가장 자주 등장한 표기**로 정했다
(동률은 사전순으로 결정적 선택). 병합 이력은 `variants` 에 보존한다.

**\|DB\| 4,279 → 4,171.**

> **규칙 1과의 경계**: 이는 **공백 축만 접는 것**이며 문자 골격 정규화(`8↔B` 등)와
> 무관하다. 지시서가 공백 무시 비교를 기본 탑재하라고 한 것과 동일한 근거이며,
> 테스트로 골격 병합이 섞이지 않았음을 강제한다
> (`test_canonicalization_only_folds_the_space_axis`).

## 3. 매칭 함수 (`src/matching/match.py`)

- **정규화 편집거리(Levenshtein) 기반 Top-K 랭킹** — 기획서 3.2 baseline 고정.
- **문자 골격 정규화 금지**. 허용되는 정규화는 대소문자 축 하나뿐.
- **공백 처리**: 원문 비교와 공백 제거 비교를 모두 계산해 **더 짧은 편집거리를 채택**
  (지시서 TASK 3-2 기본 탑재 옵션).
- **동점 처리(잠정)**: 후보 문자열 사전순으로 결정적 정렬. 신뢰도 가중은 실제 모델의
  확신도 분포가 필요하므로 **TASK 6-E 로 미룸** — 그때 tie-break 만 교체한다.

### 규칙 1 검증 — 실존 코드쌍이 서로 매칭되지 않는다

`plan.md` Phase 1-1이 확정한 12쌍 중 **11쌍이 DB에 양쪽 다 존재**한다
(`P1`/`PI` 는 한쪽만 존재). 전 쌍에 대해 다음을 테스트로 강제:

```
예측 '8135' -> top3 [('8135', 1.0), ('1135', 0.75), ('8130', 0.75)]
예측 '83'   -> top3 [('83',   1.0), ('283',  0.667), ('683',  0.667)]
예측 '(5)'  -> top3 [('(5)',  1.0), ('(15)', 0.75), ('(25)', 0.75)]
```

정확한 예측일 때 쌍둥이 코드가 1위를 가로채지 않으며, `car('8135','B13S') < 1.0`
(거리가 0이 아님)을 별도로 확인한다.

## 4. 매칭 스모크 테스트 — 측정 가능성 확인 및 목표선 보정 근거

test 크롭 762개의 정답을 인위적으로 훼손해 Top-K 응답 곡선을 측정했다.
(\|DB\| = 4,171, 폐집합)

| 입력 조건 | Top-1 | Top-5 |
|---|---|---|
| **완벽 인식 (상한)** | **100.0%** | **100.0%** |
| **공백 전부 탈락** | **100.0%** | **100.0%** |
| 1글자 오인식 | 63.4% | 86.0% |
| 2글자 오인식 | 48.0% | 66.5% |

### 읽어야 할 두 가지

**① 공백 처리 옵션이 의도대로 작동한다.** 공백이 전부 탈락해도 Top-1 이 100%다.
다중 토큰 통째 인식((a)안)의 대표적 실패 모드가 매칭 단계에서 흡수된다.

**② 🔴 Top-5 ≥ 95% 목표선은 생각보다 훨씬 빡세다.**
**1글자만 틀려도 Top-5 진입률이 86%** 다. 오류가 전부 1글자짜리라고 낙관해도,
Top-5 = 95%를 달성하려면

```
0.95 = p x 1.00 + (1-p) x 0.86   ->   p = 64%
```

즉 **예측의 최소 64%가 완전 정확(Exact-match)** 해야 한다. 실제 오류는 2글자 이상도
섞이므로 요구 Exact 는 더 올라간다. 참고로 Phase 2에서 측정한 PP-OCRv5 무조정
Exact 는 평면 45.0% / 곡면 14.1% 였다.

> **TASK 4 목표선 확정 시 반영할 것**: 기획서 3.3의 Top-K@5 ≥ 95%(초안)는
> "\|DB\| 확정 후 재보정" 조건이 붙어 있다. \|DB\| = 4,171 로 확정됐고 위 곡선이
> 나왔으므로, **Exact-match 를 부차 지표가 아니라 Top-5 목표의 직접적 제약으로**
> 다뤄야 한다. 후단 매칭이 오류를 흡수한다는 기대는 1글자 오류에 한해서만,
> 그것도 86% 수준으로만 성립한다.

## 5. 예측 원본 아카이빙 규약 (`src/matching/archive.py`)

TASK 4(baseline)·TASK 6(fine-tuned) 추론은 **반드시** 이 포맷으로 저장한다.

```json
{
  "run_id": "baseline_ppocrv4_test",
  "model": {"name": "...", "weights_sha256": "..."},
  "data": {"snapshot": "label_snapshot_v2", "split": "test", "split_seed": 42},
  "db": {"tag": "serial_db_proxy_v1", "size": 4171},
  "predictions": [
    {"crop": "...", "gt": "...", "pred": "...",
     "char_confidences": [0.99, 0.61, ...], "mean_confidence": 0.80}
  ]
}
```

**`char_confidences` 는 문자별 원본을 남긴다** — 평균만 저장하면 "한 글자만 확신이
낮은" 경우를 복원할 수 없어 TASK 6-E 의 미등록 판정 임계값 튜닝이 불가능해진다.
필수 필드가 빠지면 저장이 실패하도록 강제한다(`test_archive_rejects_records_without_confidences`).

이 규약 덕분에 "매칭 튜닝은 TASK 6-E 에서 완성한다"와 "baseline 부터 Top-K 를 잰다"가
충돌하지 않는다 — 튜닝 완성 후 저장해둔 원본에 **소급 적용**해 재계산한다.
